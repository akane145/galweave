# 跨设备记录包（导入 / 导出）

来源：多设备同步讨论后，master 选定「桌面版与浏览器版互通，希望加入记录包导入导出」。
WebDAV / 应用内自动同步**明确不在本期**（见「Not Doing」）。

## 目标

让一份「当前脚本 + 它的全部翻译记录」能从一台设备搬到另一台继续做，不需要服务器、
不需要两边同时在线，也不依赖同步盘。

## 为什么是这个形态

现状调查（`docs/DEVELOPMENT.md`「数据与备份」+ 各模块 IO 层）：

| 数据 | 存哪 | 能否随文件走 |
|---|---|---|
| 译文本身 | 项目里的脚本文件 | ✅ 本来就是 |
| 术语表 / 快捷片段 / 翻译记忆 / 统计 / 机翻基线 / 批注 / 历史快照 | `<项目目录>/.galweave/` | ✅ 跟着项目目录 |
| 进度（自动存档） | `<项目目录>/.galweave/*.progress.json` | ✅ |
| 设置（含机翻 API Key）、词典源 | **exe 同目录**（`settings.json`、`galweave.db`） | ❌ 设备相关，且含密钥与绝对路径 |

`.gitignore:13` 已忽略 `.galweave/`，所以桌面↔桌面用同步盘/git 是另一条路（见
`reliability-round/plan.md` 的讨论）。而**浏览器版没有文件系统**，它的记录全在 IndexedDB，
不随 HTML 文件走 —— 这正是记录包存在的理由：给两个形态一个共同的、可搬运的载体。

## 已定前提（master 答复）

- 场景是**桌面版与浏览器版互通**（不是两台 Windows 走同步盘）。
- 记录包**只装当前脚本及其记录**，不做整项目打包。
- **API Key、本机路径等设备配置不打包**。
- 导入**先校验并展示摘要**，再作为**独立项目**载入，避免覆盖当前工作。
- **不自动上传、不自动合并**两份离线改动。

## 架构决策

### 1. 白名单序列化，不是"排除法"

`createRecordPack` 逐字段显式挑选（`pick` / `row` / `annotation` / `stringMap`），
而不是"拷贝对象再删掉危险字段"。排除法会随上游加字段而**默认泄漏**新字段；
白名单则是默认不漏。测试直接断言序列化结果里不出现 `MUST_NOT_EXPORT` 与 `C:/private`。

### 2. 用原文逐行校验，而不是信任包内行号

导入时重新解析 `rawText`，然后**逐行比对 `p.orig === saved.orig`**，任何一行对不上就整体拒绝。
理由：译文按行号套用，**套错行把一个角色的台词写到另一个人嘴里**，比导入失败严重得多。
同时校验行数一致（多一条少一条都拒），避免"包只带了一半"造成静默错位。

### 3. 解析规则临时生效，且用完必还原

包里带 `parseConf`（脚本解析依赖它）。导入时 `setParseConf(包内规则)` → 解析 → `finally`
还原原规则。**不能在导入后把包内规则留在全局**：那会让当前打开的其他文档也用错规则解析。
异常路径同样走 `finally`，测试断言失败后 `getParseConf()` 与导入前一致。

### 4. 记录包用独立的存储命名空间

导入后的文档不是磁盘上的文件，但它要能落盘（自动存档、批注、术语、片段、历史）。
做法是给 model 一个 `recordKey`（`record:<uuid>`），`getStateKey()` 优先返回它；
各模块的 IO 层用 `isAbsPath` / `portableKey` 判断，把这类文档**一律导向 IndexedDB**：

- `glossary.activateGlossary(value, dir, key)` —— 有 key 就 `projectDir = null`，写 `record-gloss:<key>`
- `history` / `stats` / `tm` / `mtbaseline` 用 `isAbsPath(docPath)` 分流（`record:` 不是绝对路径 → IndexedDB）
- `proof.restoreState({proofPath: null, proofKey: 'proof:' + key})`

**这样导入的记录包绝不会写到用户的真实项目文件里**，也不会覆写全局术语表。

### 5. 导入不覆盖当前工作，也不假装"保存过了"

导入前先把当前活动文档 `flushDocToTab` 冻结，再开一个新标签。重复导入同名包 = 多个独立标签
（各自 `record:<uuid>`），互不影响。导入后 `docDirty = true`，保存按钮被重定向到「导出记录包」
（`saveDirect` 开头 `if (recordContext) return exportRecordPack();`）—— 因为这种文档没有磁盘路径，
"保存原文件"无从谈起。

导出成功后**只在该文档确实没再改动时**才 `clearDirty`（比对 `signature` 与 `lastSnapshotAt`），
避免"导出了一次就以为之后所有改动都存好了"。

## Not Doing

- **不做 WebDAV / 网盘自动同步**：需要处理并发写与冲突合并，而两份离线改动的合并无法在
  不理解脚本结构的前提下做对（同「保存安全」不做三方合并的理由）。
- **不做整项目打包**：多脚本打包会把体积和冲突面同时放大，而实际场景是"接着翻这一篇"。
- **不做导入时自动合并进现有文档**：包与本地记录的关系不明确时合并会丢数据，
  先按独立项目载入，让用户自己对照。
- **不打包设置/词典源**：含密钥与本机绝对路径（`dict_cmds.rs` 的 `path TEXT`）。
- **不打包进度文件**：进度是"未写回时的兜底"，记录包里已有 `rows[].translation`（最终译文），
  两者同时携带会出现"该信哪个"的歧义。

## Risks

| 风险 | 缓解 |
|---|---|
| 译文被套到错误的行上 | 逐行比对原文 + 行数校验，任一行不符整体拒绝（决策 2） |
| 导入破坏当前工作 | 独立标签 + 独立存储键；导入前冻结当前文档（决策 5） |
| 导入污染全局解析配置 | 临时生效 + `finally` 还原，异常路径也还原（决策 3） |
| 记录包把设备秘密带出去 | 白名单序列化 + 测试断言不出现 Key 与路径（决策 1） |
| 同名包重复导入互相覆盖 | `record:<uuid>` 键，重复导入开独立标签 |
| 超大包拖垮界面 | `RECORD_PACK_MAX_BYTES = 64 MiB` 上限 |
| 恶意包注入对象键 | JSON.parse reviver 拒绝 `__proto__` / `constructor` / `prototype` |

## Definition of Done

- 导出→导入往返后：译文、批注、术语、快捷片段、翻译记忆（含审核状态与说话人）、历史快照、
  机翻基线、统计都保留；原文与控制符不受影响。
- 导入是独立标签，当前工作不丢。
- 包里不出现 API Key 与本机路径。
- 行数不符 / 原文不符 / 版本不符 / 超限 / 危险键一律拒绝且不改变现有状态。
- 普通格式与离线格式（v1/v2 档案）都能往返。
